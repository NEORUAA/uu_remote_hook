# 实现说明

## Hook 的位置

UI 的画质切换逻辑会先取得协商能力，再比较用户请求与返回的最高档位。上限过低时，客户端返回「设备性能受限，最高支持%1画质。」。

本项目 Hook 能力匹配函数的返回阶段。原函数先完整执行；只有成功的 SDR 4:2:0 记录会被修改。只改画质字段，不修改错误消息或 UI 控件。

## 当前支持的结构合同

函数遵循 Windows x64 调用约定。`RDX` 为隐藏的结构返回地址，`R8D` 为色度格式，`R9B` 为 HDR 标志；函数返回值必须与输出地址相同。

| 字节偏移 | 宽度 | 字段 |
| --- | --- | --- |
| `0` | 4 | 色度格式：普通 4:2:0 为 1 |
| `4` | 4 | 画质协议档位：最高目标为 4 |
| `8` | 1 | HDR 标志 |
| `12` | 4 | 编解码器：H.264 为 1，H.265 为 2 |
| `16` | 4 | 尺寸字段 |
| `20` | 4 | 尺寸字段 |
| `24` | 4 | 结果：0 为成功，-3 为无可用记录 |

完整能力记录占 28 字节。档位编号来自客户端中的协议枚举；日志的 `ui_quality` 是另一组 UI 编号，不应直接与协议编号比较。

## 定位策略与边界

`locator.py` 先读取 PE 的 x64 unwind 表，再扫描可执行节中的候选锚点。锚点本身不能确认兼容性：定位器还要检查返回参数的来源、缺省失败结构、两条成功返回路径、质量比较，以及对应的能力记录收集函数。

能力记录收集函数必须按 28 字节遍历输入，向两类输出复制相同偏移和宽度的字段，并处理两个编解码器值。解析器可追踪有限层数的直接跳转 thunk。只使用易失寄存器的叶函数可能没有 unwind 记录，因此叶函数按可执行节和终止指令另行校验。

扫描必须得到唯一目标；零目标和多目标均视为不兼容。版本号和 SHA256 只用于诊断，不用于选择固定地址。模块基址在进程中读取，可适应 ASLR。

内存核对使用静态分析时从目标入口取得的 32 字节，并不是固定的版本特征码。若运行中的入口已经被其他工具改写，或磁盘文件与已加载映像不同，会拒绝加载。

规则适用于当前两份样本的实现形态。优化器内联、控制流重写、失败结果编码变化、无 unwind 元数据或结构字段变化，都可能需要新的验证规则。项目通过拒绝未知形态来处理这类变化。

## 进程控制

Python 控制器通过 Frida 枚举 `GameViewer.exe`。识别通过后，JavaScript 再校验 ABI、入口字节及输出地址所在的可写内存范围。运行时仍需满足格式、编解码器、成功结果和有效原档位条件，才会写入 4。

每个状态目录使用 Windows 命名 mutex 防止重复控制器。后台启动脚本使用随机启动标记确认当前控制器的就绪状态，兼容 Python venv 启动器产生父子进程的情况。停止脚本通过本地停止文件请求控制器卸载 Hook 并退出。

`.runtime/events.jsonl` 记录状态和档位，不主动采集远控画面、连接码或账号信息。失败信息可能带本机路径，提交日志前需自行检查。

旧版安装包仅解压、读取主客户端，没有启动或安装。旧版代码含更多日志，使用不同寄存器和不同目标地址；两者都通过同一定位规则。

本机已安装版本加载通用 Hook 后，日志记录画质能力 `2 → 4`，UI 档位 2、3 的请求均被接受。用户确认超清、原画均可切换且画面正常。安装 EXE 的 SHA256 保持不变。停止、重新加载和后台就绪确认也已验证。

自动测试使用自行生成的非执行 PE 数据，验证定位器接受结构合同并拒绝错误架构、枚举、布局、被调用函数、步长及歧义目标。它们用于检测定位规则退化，实际远控表现需要另外验证。
